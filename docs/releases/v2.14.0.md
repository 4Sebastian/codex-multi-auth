# v2.14.0

A long-running task no longer dies when the backend says the selected model is
at capacity. The runtime proxy waits it out and re-sends instead of burning
through the account pool. No user configuration migration is required.

Landed as [#692](https://github.com/ndycode/codex-multi-auth/pull/692), closing
[#689](https://github.com/ndycode/codex-multi-auth/issues/689).

## What was wrong

There was no handling for this error at all. A capacity response fell into the
generic `status >= 500` branch, which refunds the token, records a failure,
cools the account down and rotates to the next account.

That is the wrong shape for this particular error, and not by a small margin.
Rate limits are per account, so rotating clears them. Capacity is a property of
the **model**, so every account in the pool fails identically. The rotation
walks the pool, each account gets marked with a server-error cooldown on the way
past, the transient-attempt budget runs out within seconds, and the request ends
as a pool-exhausted 503. Start a long task and step away, and it is dead almost
immediately, having also left cooldowns on healthy accounts.

## What's fixed

The proxy now recognizes a capacity response and waits for it rather than
rotating.

- The wait backs off 2s, 5s, 15s, 30s, then 60s. An upstream `retry-after`
  header or body value wins when one is sent.
- It stops at a wall-clock deadline, `CODEX_MULTI_AUTH_MODEL_CAPACITY_RETRY_MS`,
  10 minutes by default and 1 hour maximum. The deadline covers the whole
  request, including the upstream calls themselves, not just the time asleep.
- The responding account is left completely unpenalized: its pool token is
  refunded, and it is never marked rate limited or cooled down. Selection runs
  normally on the next pass, so a healthy account is never taken out of the pool
  for an outage that was never its fault.
- If the client disconnects during a wait, the request is abandoned. No further
  upstream call is made for a response nobody is reading.
- Set the variable to `0` to restore the previous rotate-and-fail behaviour. An
  unparseable value falls back to the default rather than disabling, so a typo
  cannot silently switch the feature off.

Ordinary rate limits, entitlement failures and genuine server errors are
unchanged. Only a response whose body actually says the model is at capacity
takes the new path, and `401`, `402`, `403` and `404` are excluded outright.

## Known limitation

The exact wire shape of the capacity response is not documented, and the issue
that requested this carried no raw response. The classifier therefore matches
the message text rather than a status code, in the same way the existing
entitlement and workspace-disabled classifiers do. `at capacity`,
`model_capacity_exceeded`, `capacity_exceeded`, `currently overloaded`,
`overloaded_error` and `slow_down` are recognized.

If the phrasing you actually receive is not in that list, the feature does not
fire and behaviour is exactly as it was in 2.13.0. It cannot break a working
path. If you hit a capacity response that is not being waited out, please open
an issue with the raw body and the pattern will be widened.

## Upgrade notes

No migration is required. Nothing changes unless a capacity response arrives.

```bash
npm i -g codex-multi-auth
codex-multi-auth --version
```

The command should report `2.14.0`.
