# v2.15.0

Codex `image_gen` now works through the runtime rotation proxy. Image
generation and edit requests get the same managed OAuth, account rotation, and
usage accounting as text requests, and the built-in tool is exposed to Codex
0.154.0 sessions. No configuration migration is required.

Landed as [#694](https://github.com/ndycode/codex-multi-auth/pull/694) and
[#695](https://github.com/ndycode/codex-multi-auth/pull/695).

## What was wrong

Two separate gaps kept image generation out of reach.

The runtime rotation proxy only carried chat and completion traffic. There was
no transport for the Images API, so an image request had no authenticated path
through the managed-OAuth account pool and could not benefit from rotation,
quota failover, or the usage ledger.

Separately, Codex 0.154.0's built-in `image_gen` tool stayed hidden. The client
gates the tool on OpenAI-native auth, `requires_openai_auth`, or a recognized
actor-authorization header. This plugin uses none of the three, so pointing the
provider at the proxy was not enough to make the client expose the tool.

## What's fixed

The proxy now accepts `POST /images/generations` and `POST /images/edits`, plus
their `/v1` aliases, and forwards request bodies unchanged to the upstream
image endpoints under the existing base.

- The image routes reuse local bearer authentication, account policy and
  selection, managed OAuth refresh, account and provider headers, and response
  forwarding, the same path chat requests take.
- Ambiguous image transport failures and general image errors are not replayed
  within a single proxy request. Explicit quota and authentication rejections
  keep their existing handling.
- Image requests get a minimum five-minute upstream-header timeout.
- Images are added to the usage operation types, ledger parsing, and redaction
  normalization, so image activity is accounted for like any other request.
  See [docs/reference/image-routes.md](../reference/image-routes.md).

Provider configuration now carries a non-secret
`x-openai-actor-authorization=codex-multi-auth-local` compatibility marker in
generated TOML and canonical-home CLI overrides. That marker is what makes Codex
0.154.0 treat the provider as image-capable. It is stripped case-insensitively
at the upstream forwarding boundary, so it never leaves the machine and is never
sent as a credential. `requires_openai_auth` stays `false`, and the local
`base_url`, client bearer, model catalog, and managed OAuth rotation are
unchanged. See
[docs/reference/imagegen-provider-compatibility.md](../reference/imagegen-provider-compatibility.md).

There is no model-ID substitution and no native-auth fallback. Accounts and
installed user configuration are untouched.

## Known limitation

The marker is a version-sensitive compatibility shim against Codex 0.154.0
internals, not a supported general capability API. It grants no upstream
entitlement and cannot bypass authentication; the local bearer remains
mandatory.

The resolved server-side image model revision is not established, so this
release makes no Images 2.5 claim, and cross-request exactly-once behavior for
image edits is not promised.

## Upgrade notes

No migration is required. Existing accounts, pools and configuration are
unchanged.

```bash
npm i -g codex-multi-auth
codex-multi-auth --version
```

The command should report `2.15.0`.
