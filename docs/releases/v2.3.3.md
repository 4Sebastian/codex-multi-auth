# v2.3.3

A hardening release with nine fixes for rate limits, token refresh, streaming and storage. Routing, account selection, storage layout and the normal login flow are unchanged.

## Fixes
- One bad `retry-after` value (like a `retry-after-ms` of `999999999999`) could lock an account out for 31 years. Retry and quota windows are now capped at 7 days.
- A short `429` blip no longer benches an account for hours.
- `forecast` no longer recommends a worse account because it looked at the weekly window instead of the 5-hour one that was about to free up.
- Mid-stream errors and `response.failed` were reported as HTTP `200` success, so the account looked healthy and retry was skipped. These now count as failures.
- The SSE parser now accepts `data:value` with no space after the colon.
- Upgrading from V1 to V3 storage no longer loses rate-limit state, which could cause a burst of `429`s.
- A crash while saving the local token store can no longer leave the file truncated.
- An OAuth `expires_in` of zero or less no longer causes a tight refresh loop that burns the refresh token.
- Logs now mask this package's own `cma_local_…` tokens, along with the JWT and `sk-` tokens already masked.

## Heads up
- These fixes matter if more than one CLI or proxy shares an auth directory. Single-process users aren't affected.
- A slow token refresh could delete another process's lock, so two processes refreshed at once and one could get the account logged out. Locks now have a per-owner id.
- A routine save from a long-running proxy could put back an old token over a freshly rotated one, breaking the next refresh. Saves now pick up newer tokens from disk.
- `response.incomplete` (a token cap or content filter) is still delivered as `200` on purpose, since it carries a real partial answer.

```bash
npm i -g codex-multi-auth
```
