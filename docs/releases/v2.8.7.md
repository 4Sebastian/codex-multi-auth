# v2.8.7

Two fixes for how the wrapper reads your command line, and one for what the pinned-account error tells you when it will come back. Nothing to migrate — install and go.

```bash
npm i -g codex-multi-auth
```

## What was wrong

**Typing a prompt on the command line put Codex on the slow startup path.**

Codex's root grammar is `codex [OPTIONS] [PROMPT]`, so `codex "fix the failing test"` is an ordinary interactive session that happens to arrive with its first message already written. The wrapper read that first free word as a subcommand name instead. It matched none, so the launch fell through to the shadow-home transport meant for non-interactive request commands — and the shadow home deliberately omits the runtime SQLite state. Codex therefore rebuilt its entire thread index from rollout files on every one of those launches before it could submit the prompt you had already typed, a startup stall that grows with your session history.

Bare `codex` was never affected. Adding a prompt is what moved you onto the slow path, which is the opposite of what you would expect.

**Prompt text was being read as configuration.**

Everything after `--` belongs to the prompt, but several parts of the launcher walked the whole command line regardless:

- `codex -- --account 3 is wrong, fix it` had `--account 3` cut out of the prompt and silently pinned the run to account 3 — or refused to start with `--account 3 is out of range`, for a launch that contained no flag at all.
- `codex -- -m gpt-4 please fix this` was read as a request for `gpt-4`. That coerced reasoning settings for a model you never asked for, and on an unsupported-model retry the wrapper rewrote the model name *inside your prompt* before re-sending it.
- A `--config=cli_auth_credentials_store=...` written in prompt text counted as a caller override and suppressed the file-backed auth store the wrapper depends on.

The same boundary was wrong in the other direction for the options the wrapper adds for itself. It appended `-c cli_auth_credentials_store="file"` to the end of the command line unconditionally, which puts it in the subcommand's own positional list whenever a `--` is present. `codex exec -- ...` failed outright with `unexpected argument '-c' found`, `codex sandbox -- echo hi` handed the injected pair to the sandboxed command, and `codex mcp add t -- echo hi` wrote it into that server's stored `args` in `config.toml` — a registration that stays corrupted afterwards.

**The pinned-account 503 blamed your quota for backend outages.**

When a pinned account is unavailable the proxy returns `codex_pinned_account_unavailable` and advertises when the account recovers. It worded that deadline as "the recorded limit resets at ..." no matter what was actually holding the account back — and during a provider outage what holds it back is usually a tripped circuit breaker or a server-error cooldown. A backend incident read as a blown subscription quota.

On the most common path it named nothing useful at all. When the pinned account takes a 429 or 503 mid-request, the retry loop re-enters account selection, sees this account has already been tried, and records `already-attempted` over the real reason. The error you got back was:

```
Pinned account 1 is currently unavailable (already-attempted); the account is
expected to be available again at 2026-08-20T21:48:20.592Z
```

An internal bookkeeping token, and a deadline attributed to nothing.

## What's fixed

**Interactive launches stay on the canonical home.**

- `codex "your prompt"` keeps the real `CODEX_HOME` and its existing thread index, like a bare `codex` always has. No rebuild, no stall.
- A prompt forced with `--` counts as one, so `codex -- exec` opens a session whose prompt is the word "exec" — matching how Codex itself parses it.

**The command line is parsed the way Codex parses it.**

- Every launcher scanner stops at `--`, so `--account`, `-m`, and `--config=` written inside a prompt stay prompt text: not stripped, not read as settings, and never rewritten in place.
- The options the wrapper adds are placed on the option side of `--` instead of appended, so they reach Codex as options rather than as positional arguments to your subcommand.

**The 503 names what is actually holding the account.** The sentence now follows the real blocker, re-read from the account's live state rather than from whatever the retry loop last recorded:

| What is holding the account | What the message says |
| --- | --- |
| A rate limit, and the limit is what bounds recovery | `(rate-limited); the rate limit resets at ...` |
| A rate limit, but a cooldown or breaker ends later | `(rate-limited); the account is expected to be available again at ...` |
| An open circuit breaker | `(paused after repeated upstream errors); the next attempt is allowed at ...` |
| A cooldown | `(cooling down after upstream server errors); the cooldown ends at ...` |

The 429 case from above now reads `(rate-limited); the rate limit resets at ...`.

Only the human-readable `message` changed. The machine-readable `reason` field still reports the selection verdict verbatim, and `reset_at` and `retry_after_ms` are untouched — if you key off those, nothing about this release affects you.
